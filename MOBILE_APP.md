# Velody Mobile — App Architecture Plan

## Concept

React Native app (Android only) that consumes stems + metadata produced by Velody Desktop. Desktop handles Demucs separation; mobile handles offline playback, multitrack mix, and export.

## Stack

| Layer | Technology |
|-------|-----------|
| Mobile framework | React Native bare (Metro, no Expo) |
| Audio engine (MVP) | WebView + Web Audio API |
| Audio engine (future) | Kotlin native module (Oboe/ExoPlayer) |
| Backend | Cloudflare Worker (`cloud-worker/` in the desktop repo) |
| Auth | Personal bearer token (single user) |
| Database | Cloudflare D1 (song index) |
| Storage | Cloudflare R2 (bucket `velody`) |
| Format | MP3 320 kbps (code-ready for WAV) |

## Architecture

The backend already exists: it is the same Worker the desktop app uses for
cloud library sync (`openspec/changes/cloud-library-sync`, setup in
`cloud-worker/README.md`). The phone is just another client of it.

```
Velody Desktop              Cloudflare                   Mobile (Android)
┌──────────────────┐       ┌──────────────────┐         ┌──────────────────┐
│ Demucs separates  │       │ Worker /v1 API    │         │ React Native     │
│ stems            │──────▶│ bearer token      │◀────────│ (bare, Metro)    │
│ Upload / upload  │       │ D1 song index     │         │ Song list        │
│ all / download / │       │ presigned R2 URLs │         │ Download stems   │
│ remove local     │──────▶│ R2: songs/{id}/   │◀────────│ (RNFS)           │
└──────────────────┘       └──────────────────┘         │ WebView player   │
                                                         └──────────────────┘
```

## Data model (D1 + R2)

See `cloud-worker/migrations/0001_init.sql`:

- `songs(id, name, status pending|complete, meta_updated_at, created_at, updated_at)`
- `song_files(song_id, name, size, sha256)`

R2 keys:

```
songs/{songId}/
  drums.mp3, vocals.mp3, …   <-- the song's stems (2–6, empty ones pruned) + saved recordings
  meta.json                   <-- { meta, updatedAt }: the song's .velody (BPM grid, markers, trim, count-in, …)
```

Song ids are UUIDs generated by the desktop on first upload (`cloudId` in the
song's `.velody`).

## Desktop side (done)

The desktop app uploads, downloads, removes local copies and deletes songs
everywhere; metadata syncs last-write-wins on `updatedAt`. Nothing about
uploading happens on the phone in the MVP.

## Mobile App — Auth

Single user: the phone stores the Worker URL + personal token (Android
Keystore-backed storage, e.g. `react-native-keychain`) and sends
`Authorization: Bearer <token>` on every call. No registration, no JWT.
Multi-user accounts would be a later, separate change to the Worker.

## Mobile App — Screens

```
Connect        ← Worker URL + token (first run only)
Home           ← Song list with pull-to-refresh, search
SongDetail     ← BPM, key, chord chart (static), download button
Player         ← WebView multitrack player, mix export
Settings       ← Worker URL, cache size, forget token
```

## Mobile App — Download Flow (Manual)

1. User taps a song → SongDetail screen.
2. Shows song info + "Download" button.
3. User taps Download → app:
   - Gets presigned URLs from the Worker (`GET /v1/songs/:id/download`, 1 h expiry).
   - Downloads all files to `RNFS.DocumentDirectoryPath/velody/{songId}/`.
   - Shows progress bar (total MB, per-file).
   - Marks as downloaded locally.
4. Once downloaded → "Play" button appears.
5. Cache management in Settings: "Clear cache", size displayed.

## Mobile App — WebView Player

### Architecture

```txt
React Native Screen
  │
  ├── RN UI layer: play/pause button, timeline, chord chart,
  │   stem controls (mute/solo/volume/pan sliders)
  │
  └── WebView (invisible or minimal)
        └── Web Audio API
              ├── AudioBuffer per stem (load from file:// path)
              ├── GainNode per stem (volume, mute)
              ├── StereoPannerNode per stem (pan)
              ├── ScriptProcessorNode → connect to destination
              └── OfflineAudioContext → export mix
```

### Communication: RN ↔ WebView

- **RN → WebView**: `webview.postMessage()` or injected JS:
  - Play/pause
  - Seek to time
  - Update volume per stem
  - Update pan per stem
  - Mute/solo toggle
  - Export mix (triggers offline render)

- **WebView → RN**: `onMessage` callback:
  - Current time / progress
  - Export progress
  - Export complete (file blob)

### Stem Controls

Each stem has:
- **Mute** toggle (GainNode = 0)
- **Solo** toggle (other stems mute)
- **Volume** slider (GainNode.value = 0–1)
- **Pan** slider (StereoPannerNode.pan = -1 to 1)

### Export Mix

1. User configures stems (volume, pan, mute/solo).
2. User taps "Exportar".
3. WebView runs `OfflineAudioContext` with same graph:
   - Duration = song duration.
   - Renders all stems mixed.
   - Output → `WAV` (AudioBuffer → Blob).
4. WebView converts WAV to MP3 via `lamejs` (JS MP3 encoder in WebView).
5. Blob sent back to RN via `postMessage` → `RNFetchBlob` or `blobUtil`.
6. RN saves to `RNFS.DownloadDirectoryPath` or opens share sheet.

### Chord Chart Sync

- Parsed `chordChart` passed as initial state to WebView.
- WebView highlights current chord based on playback time.
- Tapping a chord line seeks to that position (via `RN->WebView seek`).

## Backend API

Implemented by `cloud-worker/`; contract in `src/shared/cloud.ts`. All calls
need `Authorization: Bearer <token>`.

| Method | Path | Description |
|--------|------|-------------|
| GET | /v1/health | Token check |
| GET | /v1/songs | Complete songs with files (name, size, sha256) and `metaUpdatedAt` |
| GET | /v1/songs/:id/download | Presigned GET URLs per file (1 h) |
| GET | /v1/songs/:id/meta | `{ meta, updatedAt }` |
| PUT | /v1/songs/:id/meta | Last-write-wins; `409` + current version if stale |
| POST | /v1/songs/:id/upload | (desktop) declare files, get presigned PUT URLs |
| POST | /v1/songs/:id/commit | (desktop) verify uploads, publish the song |
| DELETE | /v1/songs/:id | Delete song + files |

The phone verifies each downloaded file against its `size` and `sha256`.

## MVP Features

- Connect with Worker URL + personal token
- Songs come from the desktop's cloud sync (already implemented)
- Song list with pull-to-refresh
- Download stems to device (manual per song)
- Playback: play/pause/seek, volume + pan per stem, mute/solo
- Chord chart display with live highlighting
- Export final mix as MP3 to device
- Cache management (view size, clear)

## Phase 2 Features

- Native Android audio module (Oboe) replacing WebView for lower latency
- WAV upload support (toggle in desktop)
- Backend-triggered sync (upload from desktop triggers notification to mobile)
- Multiple profiles per device
- Favorite songs
