# Design

## Context

See proposal.md for motivation; requirements are in `specs/cloud-storage-api`
and `specs/cloud-library-sync`.

Current state that shapes the approach:

- A song is a folder `<stemsRoot>/<song name>/` holding `*.mp3` stems (2–6,
  empty stems are pruned), an optional `.velody` sidecar, and optional user
  recordings. Identity today is the folder name (`SongItem.name`); setlists
  reference songs by name.
- `scanSongsLibrary()` builds `songs:list`; `song:delete` removes the folder
  and prunes setlists.
- All `.velody` writes go through `updateMeta()` (serialized per song,
  temp-file + rename).
- `audio-server.ts` serves only files inside the stems root (`isPathSafe()`).
- The engine decodes complete stems before playing, so a song must be fully
  local before it opens.
- The user already pays for Cloudflare; Railway is not needed.

## Goals / Non-Goals

**Goals:**
- One Cloudflare-only backend (Worker + R2 + D1) with an API the mobile app
  can reuse unchanged.
- Sync logic lives in the Electron main process; the renderer only shows
  state and triggers actions.
- No change to playback, analysis, separation, export or the audio server.

**Non-Goals:**
- Real-time or background continuous sync, conflict merging per field,
  multi-user, sharing, streaming playback, syncing setlists or settings.

## Decisions

### D1. Backend: Worker + R2 + D1, in `cloud-worker/` of this repo
A single TypeScript Worker (Hono-free, plain `fetch` handler to keep it tiny)
with bindings `BUCKET` (R2) and `DB` (D1), secrets `API_TOKEN`,
`R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_ACCOUNT_ID`. Deployed with
`wrangler deploy`.
- *Alternative*: Railway Express + Postgres (MOBILE_APP.md plan). Rejected:
  two providers, a server to keep running, JWT/user tables not needed for one
  user.
- *Alternative*: separate repo. Deferred: keeping it next to the desktop app
  keeps the API types shared (`src/shared/cloud.ts` imported by both) until
  the mobile app exists; it can move to its own repo then.

### D2. Transfers use presigned R2 URLs, not Worker proxying
The Worker signs S3 `PUT`/`GET` URLs (via `aws4fetch`, 1 h expiry) and the
desktop talks to R2 directly.
- *Why*: no Worker CPU/body-size limits on 4–10 MB files, no egress through
  the Worker, and the phone gets the same flow.
- *Alternative*: stream bodies through the Worker with the R2 binding (no S3
  keys needed). Simpler, kept as fallback if presigning causes trouble.
- R2 bucket CORS is not needed for Electron main-process `fetch`; it will be
  for a future web client.

### D3. Data model
R2 keys: `songs/{cloudId}/{stem}.mp3`, `songs/{cloudId}/meta.json`.
D1:
```sql
songs(id TEXT PK, name TEXT, status TEXT CHECK(status IN('pending','complete')),
      meta_updated_at INTEGER, created_at INTEGER, updated_at INTEGER)
song_files(song_id TEXT, name TEXT, size INTEGER, sha256 TEXT,
           PRIMARY KEY(song_id, name))
```
`cloudId` is a UUID generated by the desktop on first upload and stored in the
local `.velody` (`cloudId`). Metadata JSON lives in R2 (not D1) to avoid row
size limits on long `beatTimes` arrays; D1 keeps only `meta_updated_at` for
the LWW check.

### D4. API (all under `/v1`, `Authorization: Bearer <token>`)
| Method | Path | Purpose |
|---|---|---|
| GET | `/songs` | complete songs + files + `metaUpdatedAt` |
| POST | `/songs/:id/upload` | body `{name, files:[{name,size,sha256}]}` → upserts `pending`, returns URLs for files not already present with same hash |
| POST | `/songs/:id/commit` | `HEAD`s each object in R2, verifies size → `complete` |
| GET | `/songs/:id/download` | presigned GET URLs per file |
| GET / PUT | `/songs/:id/meta` | read / LWW write (`409` + current on stale) |
| DELETE | `/songs/:id` | delete R2 prefix + D1 rows |
| GET | `/health` | token check for "Test connection" |
Token comparison uses a constant-time compare.

### D5. Desktop: `src/main/cloud/`
- `client.ts` — typed API client (`fetch`, timeouts, retries with backoff on
  5xx/network only).
- `transfers.ts` — a serial transfer queue (reuse `SerialTaskQueue` from
  `taskQueue.ts`), one song at a time, files within a song 3 in parallel;
  emits `cloud:progress` events. Pauses neither separation nor analysis
  (network-bound, not CPU/RAM-bound).
- `sync.ts` — state computation and actions (upload, download, removeLocal,
  deleteEverywhere, syncMeta).
- `settings.ts` — URL + enabled flag in `<userData>/cloud.json`; token via
  Electron `safeStorage` in the same file (encrypted base64). Never exposed to
  the renderer; the renderer only sees `{configured, enabled}`.

### D6. Library listing merges local and cloud
`songs:list` keeps scanning disk; when cloud is enabled it also fetches
`/songs` (cached in memory, refreshed on list refresh and after actions, 5 s
timeout). Matching is by `cloudId` from `.velody`, or by name for a local song
without one (reinstall / lost `.velody`); the matched id is saved to `.velody`
so the song is never uploaded twice. `SongItem` gains `sync: 'local' |
'cloud' | 'synced'`, `cloudId?`, `sizeBytes?`. Cloud-only songs have `stems: []`.
Offline → local list, and `cloud:status` reports `offline: true`.

### D7. Download is atomic
Files download into `<stemsRoot>/.velody_dl_<cloudId>/` (dot-prefixed so
`scanSongsLibrary` skips it), each verified by size + SHA-256, then
`meta.json` written as `.velody`, then the directory is `rename`d to
`<stemsRoot>/<name>/` (same filesystem → atomic). A cloud-only song whose name
is taken by a different local song is not listed (single user: not expected
in practice). Stale `.velody_dl_*` dirs are
removed at startup. The path stays inside the stems root, so `isPathSafe()`
is untouched.

### D8. Metadata LWW
`updateMeta()` stamps `updatedAt = Date.now()` on every write (one place,
covers all writers). Background analysis writes also bump it — acceptable:
the analysis result is the newest truth for those keys. Sync points: after
upload, before opening a synced song (pull if cloud newer, push if local
newer, 2 s timeout then open with local), and before "Remove from this
laptop" (push required; abort if it fails). `cloudId` and `updatedAt` are
excluded from the pushed body's comparison but included in the document.

### D9. Hashing
SHA-256 per stem computed by streaming the file in main; cached in `.velody`
as `fileHashes: {name: {size, mtimeMs, sha256}}` so the 2.2 GB backfill hashes
each file once.

### D10. UI
- Song list row: small badge (cloud / laptop / check / progress ring) and a
  context menu with the actions valid for the state.
- Delete dialog for synced songs: "Remove from this laptop" vs "Delete
  everywhere" (red, confirm text).
- Settings panel section "Cloud": URL, token (write-only field), Enable
  toggle, Test connection, "Upload all local songs".
- Opening a cloud-only song shows a download progress overlay, then loads.

## Risks / Trade-offs

- [Setlists reference songs by name; a renamed/collision-suffixed download
  breaks the link] → store `cloudId` with the downloaded song and keep the
  original name when no collision; collisions are expected to be rare.
- [Clock skew between devices breaks LWW] → single user, NTP-synced devices;
  acceptable. Server rejects `updatedAt` more than 1 day in the future.
- [Background analysis bumps `updatedAt` and could overwrite a phone edit made
  in between] → analysis only runs on songs lacking current cache, i.e. right
  after import/download; low risk, documented.
- [Leaked token gives full access to the library] → token is long random,
  stored encrypted, rotatable with `wrangler secret put API_TOKEN`.
- [R2 free tier exceeded as the library grows] → cost is ~$0.015/GB-month
  past 10 GB; the R2 dashboard shows bucket size.
- [Presigned URL clock/region issues] → fallback D2 alternative (proxy via
  binding).
- [Copyrighted audio in a cloud bucket] → private bucket, single user, no
  public URLs; same posture as files on the laptop.

## Migration Plan

1. User creates resources: `wrangler r2 bucket create velody-stems`,
   `wrangler d1 create velody`, applies `migrations/0001_init.sql`, sets the
   four secrets, `wrangler deploy`.
2. Ship desktop version with cloud disabled by default; existing libraries
   are untouched (no `.velody` rewrite until a song is uploaded or edited).
3. User enables cloud, runs "Upload all local songs" (2.2 GB backfill).
4. Rollback: disable cloud in settings — the app returns to pure local
   behavior; cloud data stays until deleted with `wrangler r2 object delete`
   / bucket deletion.
